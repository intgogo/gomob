# VIN 双 5fps 多帧快门事务

## Why

HLSD8 `4160×832` 与 RS-D550 mode25 是两颗独立、无共同硬触发的 `5fps` USB 相机。VINCreator 逆向与实机日志证明：点击快门只同时打开两路保存请求，HLSD8 跳过 3 帧，再至少收 3 张彩色和 3 张深度，用 `System.currentTimeMillis()` 保存回调时刻，在 `±100ms` 内挑一对；失败最多重采 6 轮。原厂一次实拍最终配对差为 `41ms`，没有点击瞬间同时曝光。

Gomob 旧实现把该事务错误简化成“点击后第一组合格帧”，且只等 `500ms`。真机两路 native 回调长期固定错相约 `54–59ms`；把启动间隔从 `80ms` 调到 `24ms` 后相位不变，证明不能靠固定启动延时消除。两路时间戳仍是处理后的回调完成时刻，不是传感器曝光时刻。

## How to apply

- 日常快门记录点击水位；每轮严格只消费晚于水位的新帧，跳过前 3 张 HLSD8，至少收齐 3 张彩色和 3 张深度。
- 在整批候选中选择回调时间差全局最小的一对，不再返回第一组合格帧；单轮最多等 `5s`，失败最多重采 6 轮。
- 普通预览缓存新鲜度仍为 `250ms`；burst 内早期帧属于同一采集事务，不能因收齐 3+3 期间变旧而误删。
- 手机与服务端使用同一 `100ms` 回调门；`100000us` 通过，`100001us` 拒绝。
- UI、日志与元数据必须称“回调差”，并写明 `timestampKind=host_callback_monotonic`，禁止称为曝光同步。
- `100ms` 不代表曝光级同步。最终 VIN 完全重合仍须取得 PTS/SCR，或用同步光学事件校正两条处理管线，并证明曝光等效差 `≤25ms`。
- 回归跑 `vin_rgbd_pairing`、`eys3d_vendor_cpp`；真机确认 `capture burst` 至少 3+3、全局最小差、原始 RGBD 落盘和服务端响应。
