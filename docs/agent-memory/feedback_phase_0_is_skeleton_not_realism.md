# Phase 0 是骨架不是真实, 但骨架也不许造假

早期阶段搭**采集 / JNI / 数据通道骨架**是对的, 也是必经的. 但"骨架阶段"和"允许造假"是两件事: 骨架可以缺重建质量、缺多视角配准、缺纹理烘焙, **但流过骨架的每一帧、每一次 native 调用都必须是真的**. 不能用硬编码深度、假位姿、离线资产把骨架伪装成已经实现了真实 RGBD 重建.

**Why:**
- 项目魂(扫描真实化): 真实 = 扫描结果经得起近距离量测和反复复现, 不能用漂亮预览 / 硬编码姿态 / 单帧 demo / 离线资产伪装真实 RGBD 链路. 骨架阶段一旦塞进假数据, 上层就开始信任假契约, 越往后越难拆.
- "能在屏幕上显示点云" ≠ "重建是真的". 显示对了不等于深度值、外参、时间戳是真的. 骨架的价值在于把**真实数据通道**打通, 而不是把屏幕填满.
- 骨架造假违反 [第一性原理不妥协](principle_first_principles_no_compromise.md): stub(固定值返回 / 单分支硬编码 / demo 数据伪装真实链路)直接接真实数据源, 不留.

**骨架阶段允许缺 vs 不许假:**

| 维度 | 骨架可以缺(后续 Phase 补) | 骨架不许假(从第一天就得真) |
|------|--------------------------|---------------------------|
| 深度帧 | 重建质量、补洞、滤波调参 | 深度值必须来自相机真出帧, 不写死常数 / 不喂离线 .png |
| 位姿 | 多视角配准精度、PGO 收敛 | 位姿必须来自真实采集 / 真实标定外参, 不硬编码摆好的姿态 |
| JNI 通道 | native 重建算法可先空实现 | 帧契约(分辨率 / 时间戳 / 像素格式)必须是真的, DirectByteBuffer 真的指向相机数据 |
| native 调用 | TSDF / Marching Cubes 可后置 | `NativeBridge` 真的过 JNI 调到 C++, 不在 Kotlin 侧伪造返回 |
| 同步 | 重同步策略可简化 | RGB / depth 时间戳必须真带、真比对, 偏差超阈值真丢帧 |

**How to apply:**
- 搭骨架前先查 [历史上下文](principle_context_first.md), 再想: 这条通道的真实数据源在哪? 现在能不能直接接? 能接就接, 别先填假值占位.
- 骨架的"未完成"用空实现 + 明确 TODO 表达, 不用假数据表达. native 重建没写好就让 `NativeBridge` 返回明确的"未实现 / 空结果", 让上层知道这里还没真, 而不是返回一团看起来像点云的假数组.
- 缺的是下游模块时按 [整体改不打补丁](feedback_holistic_not_patching.md) 去补下游, 不在采集骨架里加假 fallback / 退化路径冒充已实现.
- 厂商 SDK / 真机不在手时, 走 host harness 或通用 UVC 真链路自测(见 [mock 只在 IO 边界, 守恒不变](feedback_mock_first_io_conserved.md)): mock 只替换最外层 USB / 文件 IO, 帧契约和 native 调用仍是真的; 不把整条重建链路换成离线资产回放还宣称跑通了.
- 命中扫描质量 / 配准 / 同步等不确定模块时, 骨架阶段就该建 harness(见 [重要不确定模块必须建 harness](feedback_harness_mandatory.md)), 让 `tests/harness/scan_quality`、`device_sync` 等用真采样数据出可判定结论, 而不是靠"屏幕上看着像"判断骨架是否真.
- 验收骨架时跑真链路自测(见 [自测过才算完成](feedback_self_test_before_claim_done.md)、[业务验证不止于 UI](feedback_business_verification_not_ui_only.md)): 看 logcat 帧时间戳、看 harness analyze.py 结论、量点云尺度, 不把"编译过 / 预览出图"当骨架达标.
- 真实重建质量(多视角配准、端云融合、纹理一致性)是 Phase 1+ 工作, 不是骨架子步; 骨架只负责把真数据真通道铺到位, 不负责假装重建已经做完.
