# 先设计后实现，禁止最小化修改思维

遇到问题时，先不考虑现有设计，直接从第一性原理进行设计，再回过头考虑怎么实现这个新设计。
绝不从现有代码出发做"最小化修改"。

**Why:** 产品研发阶段本来就是各种尝试。如果现在就以"最小化修改"思路做事，会不断在错误基础
上打补丁，最终堆成屎山。正确做法是：发现架构不对 → 重新设计正确的 → 再看现有代码哪些能
复用、哪些该扔。

**How to apply:**
- 发现问题时，第一反应不是"现有代码怎么改最少"，而是"如果从零开始这个问题的正确解法是什么"
- 先写设计（§xxx），把正确模型定义清楚
- 然后才看现有代码：能复用的复用，该重写的重写，该删的删
- 不要出现"这样改动最小""对现有系统影响最小"这类措辞作为选择方案的理由
- "影响范围大"不是拒绝正确方案的理由 — 产品阶段就是该大改的时候
