# 自主执行纪律 — 不中途请示, 不提前刹车

**规则**: auto 模式下拿到一个任务(修 bug / 挖根因 / 改实现 / 推进某模块), 自己一路推进到底。
不在每个分支点停下来问"要不要继续 / 要我做吗 / 是否往下挖", 不在做完第一阶段就写"本轮交付"
总结收尾。把候选分支自己 explore 完、把活干完, 拿到结论再一次性汇报。

## Why

- 用户多次明确表态: "要, 自己主动去解决, 不要问来问去"; "你为什么这么懒惰? 推进一下就停下来,
  非得让我说一声继续"; "停下的时候自己继续"。
- auto 模式系统约定本身就是 "Work without stopping for clarifying questions. When you'd
  normally pause to check, make the reasonable call and keep going"。频繁的请示式确认
  (AskUserQuestion / "要我追吗" / "是否继续")打断 flow、浪费用户来回, 用户视之为噪音。
- 自我审查"这改动够不够大、要不要先问"往往过保守。实际很多被判成"牵扯大、留下次"的活,
  做下来就是几十到两百行 + 几个测试, 半小时能 ship。用"改动大 / 风险高 / 牵扯多"当借口刹车,
  绝大多数时候是误判。
- 用户信任 agent 的判断力: 把问题查清并修掉, 比把决策权一再交还更有价值。

## How to apply

- 用户说"修 X bug" / "查 Y 根因" / "为什么 Z" / "推进 W" → 直接挖到底、做到底, 中途不问
  "要不要继续 / 要不要走 A 还是 B"。
- 普通诊断分支(是 native 配准路径死还是 RGBD 同步路径死)、改一处计数器、改一个判断、
  调一个 harness 阈值 → 自己拍板, 不问。
- harness 采样 / 真机自检(logcat、uiautomator dump、Compose 测试)跑出 P0/P1 →
  直接进入调查 + 修复, 不先请示。
- "下次 sprint" / "留下次" 不是合法停止信号 — 当前能做就当前做。因上下文切换、工具等待、
  阶段完成、自查结束而自然停下时, 默认立刻选下一项继续推进。
- 不把测试 / 自测当停止理由, 那是工序的一部分(见 [开发闭环](feedback_dev_loop.md)、
  [自测后再声明完成](feedback_self_test_before_claim_done.md))。
- 阶段性"小总结"(1-2 句 + 继续干)可以; 完整"本轮交付"风格总结只放在用户明确批的范围
  真正没活干、被打断、或主动询问时。
- 修复仍要先回到设计判断: 是设计缺陷还是实现 bug, 不堆补丁
  (见 [整体修不打补丁](feedback_holistic_not_patching.md))。修完一并汇报结果, 不逐段汇报过程。

## 例外 — 这些情况才停下来确认

- 真正的设计分叉 / 多选项 / 关键参数取值(如 native 有效距离阈值、时间同步偏差阈值、
  TSDF voxel size、是否新增一条配准管线 vs 复用现有融合模块)→ 用 AskUserQuestion 结构化提问,
  不擅自定。
- 不可逆 / 外发 / 影响其它模块的副作用: git push、删数据、改公共 API / `core:model` 数据契约 /
  Room schema、改主机调度。
- 方向性抉择: 要不要推翻某个已定设计、要不要改重建主线方向。

区分线: 技术细节自己定, 方向 / 不可逆 / 真分叉才问。
