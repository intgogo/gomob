# 项目级硬规则 — 第一性原则选最优, 开发设计不做妥协

**立项**: 2026-05-03（沿袭 gogame 同名原则；本项目立项即采纳）

## 规则

遇到选择时，按第一性原则推导最优解，开发和设计上不做妥协。

## 为什么

之前 Agent 工作中常出现"列出 A/B/C 选项 → 默认选最小改动"的模式，把
"风险最小"误当"最优"。这违背"做对的事比快做事重要"的本意 — 在系统正确的
方向上一步一步真做对的事，比走 10 个小妥协累加出来的"半正确"更有价值。

典型反例：
- 看到 stub（`v1 桩实现`、`TODO 后续优化`）留着不改，因为"接真实数据可能破"
- 设计模块 A 时为了避开模块 B 的不就绪，在 A 这里加 fallback / 退化路径
- 三选项里因 A/B 跨模块大就选 C 最小，不论 A/B 是否更对

## 如何应用

1. **先推导"何为对"**：任何分叉前先回到第一原理 — 这个系统的目标是什么 /
   因果链是什么 / 公理是什么 / 正确路径是什么。把答案写下来。

2. **选真正最优**：不是"风险最小"那个。实现成本高 / 跨模块大不是退到妥协的
   理由。难和对的，就直接做。

3. **临时方案明记**：真没想清楚正确解时才允许探路。但要在代码 / 注释 / commit
   明确写"这是探路，终态是 X" + TODO 指向终态。不要用"v1 桩""MVP"之类
   包装去蒙混次优。

4. **跨模块协调**：遇到"模块 B 还没就绪"时不能在 A 这边退化。是补 B，而不是
   A 妥协。

5. **stub / 硬编码**：现有 stub（返固定值 / 单分支硬编码）应直接接真实数据源
   / 真实状态机，不因"不知道改了会不会破"留 stub。

## §分叉自检 4 问（工具化）

任何方案分叉处，决定推荐项前**必须**走完这 4 问。任一问没有清晰答案，不准进下一步：

1. **根本因果是什么？** — 不是"用户说要 X"，是"为什么需要 X / 它解决什么因果链上的问题"。写下来。
2. **从零设计会怎么做？** — 假装现有代码不存在，不受任何约束，第一性最优解是什么？写下来。
3. **方案与零约束设计的差距在哪？** — 差距是**真实约束**（硬件物理 / 上游 SDK / 平台 API）
   还是**"我懒得动"**（跨模块大 / 实现成本高 / 怕破东西）？后者不是退妥协的理由。
4. **触发反模式清单了吗？** — 任何一条命中，立刻回到第 2 问：
   - "先做个简单版本，后面再优化" — 临时方案没绑死时间和触发条件
   - "这块先 hardcode，等 B 模块好了再换" — fallback 替代了真问题
   - "在 A 里加个 if 处理 B 没就绪的情况" — 应该补 B 而不是补 A
   - "保留旧逻辑做兜底" — 兼容性蒙混次优解
   - "v1 桩 / MVP 后续优化" — 包装词蒙混次优

**Why 工具化**：之前规则在脑子里，实际工作中会被"沉浸感 + 时间压力"绕过。
4 问是强制 pause + 落字，让 Agent / 自己**看见**自己有没有偷懒。

**How to apply**：在 brainstorming 类对话 / 写设计 spec / 写 TODO 章节前显式
走一遍，答案写到 spec 或 TODO 节里（不是脑子里）。走完之后再提"推荐方案"。

## 在本项目（gomob）的具象表达

- **同步性**：RGBD 双摄不同步是物理上的事实，不是"差不多就行"。时间戳偏差超
  阈值的帧丢弃，不"凑合用"。
- **JNI 边界**：散点 `external fun` 一律拒绝合并 — `core:native-bridge.NativeBridge`
  是唯一通道。
- **Berxel SDK 缺位**：不接受"在 native 端写一份伪 Berxel 接口"绕过 — 走通用
  UVC 通用路径，**对**地补，不**糊**地补。
- **标定**：内/外参标定一次性产出 + 跨会话复用，不接受每次扫描"重新猜"。
