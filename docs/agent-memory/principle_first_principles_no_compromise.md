# 项目级硬规则 — 第一性原则选最优, 开发设计不做妥协

**立项**：2026-05-03（沿袭 gogame 同名原则；本项目立项即采纳）

## 规则

遇到选择时，按第一性原则推导最优解，开发和设计上不做妥协。

遇关键问题，先调研参考行业最佳 / 最成功的解决方案，再思考突破超越，切莫闭门造车。

## 为什么

之前 Agent 工作中常出现"列出 A/B/C 选项 → 默认选最小改动"的模式，把
"风险最小"误当"最优"。这违背"做对的事比快做事重要"的本意 — 在系统正确的
方向上一步一步真做对的事，比走 10 个小妥协累加出来的"半正确"更有价值。

对 gomob 而言尤其致命：项目魂是**扫描真实化** — 结果要经得起近距离量测和反复
复现。每一次"差不多就行"的妥协（硬编码姿态、伪外参、单帧 demo、离线资产伪装
真实 RGBD 链路）都直接腐蚀真实性，最后变成一个"看着像但量不准"的假扫描仪。

典型反例：
- 看到 stub（`v1 桩实现`、`TODO 后续优化`）留着不改，因为"接真实数据可能破"
- 设计模块 A 时为了避开模块 B 的不就绪，在 A 这里加 fallback / 退化路径
- 三选项里因 A/B 跨模块大就选 C 最小，不论 A/B 是否更对

## 如何应用

1. **先推导"何为对"**：任何分叉前先回到第一原理 — 这个系统的目标是什么 /
   因果链是什么 / 公理（同步性、零拷贝、有效距离、精度规格）是什么 /
   正确路径是什么。把答案写下来。

2. **选真正最优**：不是"风险最小"那个。实现成本高 / 跨模块大不是退到妥协的
   理由。难和对的，就直接做。

3. **临时方案明记**：真没想清楚正确解时才允许探路。但要在代码 / 注释 / commit
   明确写"这是探路，终态是 X" + TODO 指向终态。不要用"v1 桩""MVP"之类
   包装去蒙混次优。

4. **跨模块协调**：遇到"模块 B 还没就绪"时不能在 A 这边退化。是补 B，而不是
   A 妥协。

5. **stub / 硬编码**：现有 stub（返固定值 / 单分支硬编码）应直接接真实数据源
   / 真实状态机，不因"不知道改了会不会破"留 stub。

6. **不向用户提"快速修复 vs 正确修复"二选一**（吸收自 [不做妥协](feedback_no_compromise.md)）：
   发现架构问题时，不要列"调参凑合 / 修修补补 / 根本修复"让用户选 — 直接给正确
   方案 + 工作量评估。用户不需要你帮他选"省事路径"，你需要替他守住"做对的事"
   的下限。工作量大就说清楚步骤，不替用户预设妥协。

7. **从零设计在先，不做"最小化修改"**（吸收自 [第一性设计](feedback_first_principles_design.md)）：
   发现问题时，第一反应**不是**"现有代码怎么改最少"，而是"如果从零开始这个问题
   的正确解法是什么"。先写设计（架构 / 设计文档），把正确模型定义清楚，**然后才**
   看现有代码能复用 / 重写 / 删。"影响范围大"不是拒绝正确方案的理由 — 产品阶段
   就该大改。

8. **先调研行业最优，再谈突破，不闭门造车**：遇关键问题（架构选型 / 重建算法 /
   配准策略 / USB 协议 / 数据结构 / 性能…），先调研行业最佳与最成功的开源/论文/
   工业实践（如 Open3D multiway registration、TSDF、libuvc/libusb 现代栈），搞清它们
   "为什么这么做 + 解决了什么 + 局限在哪"，把这个作为最优解的**下限**；然后才在
   理解之上思考如何突破超越。不允许凭空臆想一个"自以为最优"的方案而不参考既有
   最佳实践 — 那既可能重复造轮子，也可能踩别人早已绕开的坑。第一性原理是**推导
   工具**，不是无视前人成果的借口：用它去**理解**行业方案为何如此，再判断哪里
   可被超越。

## §分叉自检 4 问（工具化）

任何方案分叉处，决定推荐项前**必须**走完这 4 问。任一问没有清晰答案，不准进下一步：

1. **根本因果是什么？** — 不是"用户说要 X"，是"为什么需要 X / 它解决什么因果链上的问题"。写下来。
2. **从零设计会怎么做？** — 假装现有代码不存在，不受任何约束，第一性最优解是什么？写下来。
3. **方案与零约束设计的差距在哪？** — 差距是**真实约束**（硬件物理 / 上游 SDK / 平台 API）
   还是**"我懒得动"**（跨模块大 / 实现成本高 / 怕破东西）？后者不是退妥协的理由。
4. **触发反模式清单了吗？** — 任何一条命中，立刻回到第 2 问：
   - "先做个简单版本，后面再优化" — 临时方案没绑死时间和触发条件
   - "这块先 hardcode，等 B 模块好了再换" — fallback 替代了真问题
   - "在 A 里加个 if 处理 B 没就绪的情况" — 应该补 B 而不是补 A
   - "保留旧逻辑做兜底" — 兼容性蒙混次优解
   - "v1 桩 / MVP 后续优化" — 包装词蒙混次优

**Why 工具化**：之前规则在脑子里，实际工作中会被"沉浸感 + 时间压力"绕过。
4 问是强制 pause + 落字，让 Agent / 自己**看见**自己有没有偷懒。

**How to apply**：在 brainstorming 类对话 / 写设计 spec / 写 TODO 章节前显式
走一遍，答案写到 spec 或 TODO 节里（不是脑子里）。走完之后再提"推荐方案"。
与 [批判性思考不做应声虫](feedback_critical_thinking_not_yes_man.md) 联动：4 问推
导出的正确解若与用户预设冲突，直说，不顺着错的方向往下做。

## §调参 / 实现操作面 4 条硬规则

含不确定性或可调参数的模块（同步阈值、ICP / 多视角配准阈值、TSDF voxel size、
滤波窗口、深度有效距离裁剪等），落实时遵守：

1. **观测先于调参** — 含可调参数的模块，第一步必须是 instrument（harness 采样 /
   logcat 度量 endpoint）。看不见的状态不允许调参。
2. **算术机制必有不变量测试** — `seq % N` / throttle / phase window / 帧配对计数
   必须有统计意义的不变量验证（例：N 帧采集后配对率 ≈ 预期），而非"某个 case 不崩"。
3. **真实路径优先，fallback 限哑桩** — 含真实数据路径（Berxel / UVC / 云端配准）时，
   离线 / mock fallback 只允许 1-3 个 return，不允许伪装成完整链路反客为主。参见
   [Mock 优先且 I/O 守恒](feedback_mock_first_io_conserved.md)。
4. **度量脱节先改度量** — harness 实测与设计意图脱节 ≥30%，先怀疑度量错（坐标系 /
   单位 / 时间戳基准），不是改实现凑数字。

## 在本项目（gomob）的具象表达

- **同步性**：RGBD 双摄不同步是物理上的事实，不是"差不多就行"。时间戳偏差超
  阈值的帧丢弃，不"凑合用"。
- **JNI 边界**：散点 `external fun` 一律拒绝合并 — `core:native-bridge.NativeBridge`
  是唯一通道。
- **Berxel SDK 缺位**：不接受"在 native 端写一份伪 Berxel 接口"绕过 — 走通用
  UVC 通用路径，**对**地补，不**糊**地补。
- **标定**：内/外参标定一次性产出 + 跨会话复用，不接受每次扫描"重新猜"。

## 与现有规则的关系

- 单元测试验证"代码对不对"，harness 验证"行为好不好"（见
  [harness 强制](feedback_harness_mandatory.md)），本原则验证"选择对不对"。
- 是 [批判性思考](feedback_critical_thinking_not_yes_man.md)、
  [整体重构非打补丁](feedback_holistic_not_patching.md) 的上位原则；它们是本原则
  在具体行为上的落地。
