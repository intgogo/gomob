# 设计决策风格偏好

**跟 [第一性原理不妥协](principle_first_principles_no_compromise.md) 的关系**：principle 是"决策层硬规"（遇分叉如何推导最优解），本文是"风格层偏好"（项目长期审美 / 价值观）。两者冲突时 principle 优先于本文。

## 1. 激进决策，"该动就动"

在开发早期阶段，面对"小改动 vs 彻底重构"的选择时，不要默认选保守路径。倾向于
"一次做到位"。验证时不要问"要不要?"而是问"改多深?"。但仍需列出代价让用户拍板。

> 跟 principle 的分叉自检联动：先走完自检推导出对的方向，本文再决定推荐项的"激进度"。

## 2. 长期主义

设计数据契约、评估指标、参数学习时，永远优先考虑长期效果。遇到"短期看 demo 漂亮"
的方案要警觉。扫描真实化是长期主线：宁可把配准 / 融合 / 标定做扎实，也不要靠漂亮
预览或硬编码姿态先交差。

## 3. 反馈要严格，禁止讨好

跟 [批判而非迎合](feedback_critical_thinking_not_yes_man.md) 同源：

- 发现问题直接说，不要"可能有点问题"这类模糊表达
- 分严重度分级，让用户清楚知道哪些必须修
- 好的地方也要说，但重点是找问题

## 4. 文档分层偏好（设计 vs 实施）

- 设计文档回答"为什么"，实施文档回答"怎么做"
- 不要把数据类签名、proto schema、跨模块 API 契约塞进设计文档
- 新增大系统时默认两份文档起步

## 5. 边界纯粹

- 不要把数学（深度反投影、外参变换、TSDF 积分）和 UI / 业务逻辑混
- 数学走 native（C++），上层 Kotlin 只做编排和呈现；JNI 边界统一收口在 `core:native-bridge`
- 偏好削减系统的复杂度（删除 vs 新增），让每个模块职责清晰
