# 设计决策风格偏好

## 1. 激进决策，"该动就动"

在开发早期阶段，面对"小改动 vs 彻底重构"的选择时，不要默认选保守路径。倾向于
"一次做到位"。验证时不要问"要不要?"而是问"改多深?"。但仍需列出代价让用户拍板。

## 2. 长期主义

设计决策模型、评估指标、参数学习时，永远优先考虑长期效果。遇到"短期 KPI 看起来好"
的方案要警觉。

## 3. 反馈要严格，禁止讨好

技术 review 和设计讨论中：
- 发现问题直接说，不要"可能有点问题"这类模糊表达
- 分严重度分级，让用户清楚知道哪些必须修
- 好的地方也要说，但重点是找问题

## 4. 文档分层偏好（设计 vs 实施）

- 设计文档回答"为什么"，实施文档回答"怎么做"
- 不要把数据类签名、proto schema、跨模块 API 契约塞进设计文档
- 新增大系统时默认两份文档起步

## 5. 边界纯粹

- 不要把数学（深度反投影、外参变换、TSDF 积分）和 UI / 业务逻辑混
- 数学走 native（C++），上层 Kotlin 只做编排和呈现
- 偏好削减系统的复杂度（删除 vs 新增），让每个模块职责清晰
